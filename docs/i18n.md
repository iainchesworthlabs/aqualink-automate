# Web UI internationalization (i18n)

*How the web UI's translation layer works and how to add a language. The
roadmap and surface analysis live in [docs/i18n-scoping.md](i18n-scoping.md);
this doc describes what is implemented: the catalog infrastructure, full
English string extraction, and the shipped locales.*

**Shipped locales:** English (`en`, default/fallback), German (`de`), Arabic
(`ar`, RTL — the document `dir` flips; the CSS logical-properties pass is
still pending, see the scoping doc's Phase 3), Japanese (`ja`).

## Architecture

- **Catalogs** are plain JS registration files under `assets/web/i18n/`, one
  per locale, each assigning a flat `"namespace.key" → string` map into
  `window.AquaI18n.catalogs.<locale>`. English (`i18n/en.js`) is included
  statically in `index.html` before every other app script, so the default and
  fallback catalog is always available synchronously — no fetch race, no flash
  of raw keys, works offline. A **saved** non-English locale is loaded
  synchronously at boot too (parser-blocking `document.write` from the
  runtime), so a returning user's first paint — including any boot-time toast
  — is already in their language. Catalogs for locales *switched to* during a
  session load on demand via `<script>` injection and swap in reactively.
- **Runtime** is `assets/web/scripts/i18n.js`: the locale registry
  (`SUPPORTED_LOCALES`), an Alpine store (`$store.i18n`), the `$t('key',
  {params})` / `$tn('key', count)` template magics, and `window.AquaI18n.t()`
  for plain-function call sites (stores, views, components). Lookup order:
  active locale → English → the key itself (with a one-time console warning,
  so a missed extraction is visible in dev tools).
- **Locale resolution**: explicit user choice (Settings → Appearance →
  Language) is stored in `localStorage` (instant boot) and mirrored to the
  server under `preferences.ui.locale` (cross-device; the server value wins on
  conflict). A user who never chose follows `navigator.language`. `<html
  lang>` and `<html dir>` track the active locale; locales registered with
  `dir: 'rtl'` flip the document direction (no RTL locale ships yet — the CSS
  logical-properties pass is a later phase, see the scoping doc).
- **`/api/preferences` `ui` merge**: the opaque `ui` object merges shallowly
  at its top level on PUT, so `ui.locale` and `ui.chemistryBands` (written by
  independent frontend features) never clobber each other; a top-level null
  deletes the key. See `assets/web/api/swagger.yaml` and
  `TestSuite_PreferencesService/ApplyJson_UiMergesTopLevelKeys`.

## Key conventions

- Flat dot keys, namespaced by surface: `nav.*`, `login.*`, `dash.*`,
  `detail.*`, `diag.*`, `devcard.*`, `trends.*`, `sched.*`, `settings.*`,
  `about.*`, plus shared `common.*`, `status.*`, `cmd.*`, `alert.*`,
  `toast.*`, `time.*`, `tier.*`, `chem.*`, `swg_health.*`, `day.*`.
- Placeholders are `{name}` and are substituted by `t()`; never rebuild
  sentences by string concatenation — word order differs across languages.
- **Number-typed** placeholder values are rendered with `Intl.NumberFormat`
  for the active locale, so the digits themselves localize (Arabic renders
  Eastern Arabic-Indic numerals — pinned via the registry's
  `numberLocale: 'ar-u-nu-arab'` because bare `ar` resolves to Latin digits in
  some engines). Pass numbers as numbers; a pre-formatted string (e.g.
  `toFixed()` output) passes through untouched.
- Keys ending in **`_html`** may contain markup (bound with `x-html`; the
  content is static catalog text, never server data). Translations must
  preserve the tags.
- **Plural keys** carry a CLDR category suffix (`.one`, `.other`, …) and are
  looked up via `tn(key, count)` / `$tn` using `Intl.PluralRules` (e.g.
  `sched.conflicts.one` / `sched.conflicts.other`).

## Value formatting (Phase 1)

Displayed values format through `window.AquaI18n` helpers, which follow the
**selected** locale (not the browser locale) including the registry's
`numberLocale` pin, and re-render reactively on a locale switch:

- `formatNumber(value, intlOptions)` — locale digits/separators; template
  sugar `$n(value)` and fixed-decimals `$nf(value, digits)`.
- `formatTemperature(value, units)` — takes the wire dual-unit object
  (`{celsius, fahrenheit}`) and the server `temperature_units` preference
  (`'Celsius' | 'Fahrenheit'`), renders via `Intl` unit formatting. The pool
  store holds the preference (`$store.pool.displayUnits`, loaded with the
  initial data, pushed by Settings on save) and exposes the display getters
  (`poolTemp`, `poolSetpointDisplay`, …) — raw wire values stay in state so a
  units/locale change re-renders everything.
- `formatTime(value)` / `formatDateTime(value)` — `Intl.DateTimeFormat` in the
  active locale (server start time, last-update, last-seen stamps).

The WebSocket `TemperatureUpdate` payload carries the same raw dual-unit
objects as REST (the old pre-formatted string path hardcoded Celsius). On the
MQTT side, the HA setpoint *number* entities follow the preference
(template/unit/range + command interpretation, republished on change), while
temperature *sensors* stay declared °C — HA converts sensors itself (see
`docs/mqtt-home-assistant.md`).

Known exception: the Trends chart renders in °C regardless of the preference
(its axis/scaling is Celsius); converting the whole chart is a follow-up.

## What is deliberately NOT translated

- **Device-originated text**: aux/device labels, pool names, panel screen
  lines, controller program names — these arrive over RS-485 (or are
  user-configured) and pass through verbatim.
- **Technical tokens**: backend enum values used as wire/comparison values
  (the display layer maps the known ones via `status.*` / `swg_health.*`
  catalog keys and falls back to the raw name for unknown values), log
  severity levels and channel names, JSON field names, MQTT payloads, units
  attached to raw diagnostics, endpoint paths, the brand name.
- **Backend prose** (HTTP error bodies, alert `detail` text) still arrives in
  English — converting those to symbolic codes + params is Phase 2 of the
  scoping doc.

## Adding a language

1. Copy `assets/web/i18n/en.js` to `assets/web/i18n/<code>.js`, change the
   registration line's locale code, and translate the **values** (never the
   keys). Keep `{placeholder}` names, `<code>…</code>` contents, technical
   tokens and brand names untranslated.
2. Register the locale in `SUPPORTED_LOCALES` in `assets/web/scripts/i18n.js`
   with its own-language name (endonym) and text direction (`ltr`/`rtl`).
3. Run the guard: `pwsh scripts/check-i18n-keys.ps1 -Root <repo-root>`.
4. The new catalog ships automatically: the build copies and packages
   `assets/web` recursively, and the service worker precaches `i18n/en.js`
   (other locales are cached on first use by the runtime caching layer).

## Testing / guard rails

Three layers keep i18n from silently rotting as features evolve:

1. **`scripts/check-i18n-keys.ps1`** (static; runs in CI as the
   `i18n-catalogs` job in `.github/workflows/ci.yml`): every key referenced in
   code must exist in `en.js`; every locale must have exact key parity with
   `en.js`; every translated value must carry exactly the English value's
   `{placeholders}`.
2. **`e2e/i18n.spec.ts` — runtime behavior**: lookup/placeholder/plural/
   fallback semantics, the Settings language picker, localStorage persistence
   across reload, per-locale catalog loading, and the `<html lang>`/`<html
   dir>` contract (Arabic ⇒ `rtl`).
3. **`e2e/i18n.spec.ts` — guard rails**: walking every route must produce zero
   `[i18n] missing catalog key` console warnings (catches a `t()` call whose
   key was never added), and a runtime **pseudo-locale scan** (every catalog
   value wrapped in `⟦…⟧`, then the DOM is walked for visible Latin text
   without the markers) catches brand-new hardcoded strings that bypassed the
   catalog entirely. Legitimate untranslated content (device labels, wire
   tokens, endpoints) is covered by the spec's exempt-selector list or a
   `data-i18n-exempt` attribute on the element.

   **Known blind spot:** the pseudo-locale scan ignores text with fewer than
   three consecutive Latin letters, so short duration/unit abbreviations
   ("1m", "7d") pass unnoticed — those must go through the `time.abbr_*`
   catalog keys and need human review when touched (this exact miss shipped
   once in the chart filters).

Backend side: `/api/preferences` `ui` merge behavior is covered by
`TestSuite_PreferencesService/ApplyJson_UiMergesTopLevelKeys`.
